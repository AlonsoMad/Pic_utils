## Scope

Implemented process supervision and the memory guard (architecture §8.2,
§8.4-§8.6):

- `src/pic_utils/runner/memory.py`: `MemoryGuard` — `app_rss_mb`,
  `worker_rss_mb` (psutil; direct children by default), the §8.6 estimate
  (`bytes_per_image * min(2 + 2*image_steps, 8)`, exactly 8 for a `LAYERS`
  step, bypassed steps excluded), `admission` → admit/defer/fail against
  the ceiling minus the 512 MB reserve, `can_hold_sources` preflight,
  `should_recycle` (RSS > ceiling/workers), and `max_workers` clamping.
- `src/pic_utils/runner/pool.py`: `SupervisedPool` — spawn context +
  `ProcessPoolExecutor` (never fork), a drain thread consuming the workers'
  event queue (PID registry, in-flight map, log forwarding to the parent's
  single `run.log` writer), a watchdog killing experiments that exceed
  `experiment_timeout_s`, crash detection via `BrokenProcessPool` futures,
  graceful `cancel_pending`, force `kill_all`, `rebuild` bounded at 3 per
  run (`pool.unstable`), and `shutdown`.
- `src/pic_utils/runner/worker.py` (sequential ownership note below): the
  §8.6 worker-side check — an experiment aborts with `memory.limit` when
  `psutil.virtual_memory().available` is below its estimate.
- `WorkerLog` gained an optional formatted `traceback` (§18.3: full
  tracebacks to `run.log`).
- Tests: `tests/runner/test_pool.py` (22) with real spawned workers: submit
  + result, crash detection + rebuild, rebuild limit, watchdog kill,
  cancel-queued-not-running, force kill, log forwarding, and the full
  MemoryGuard boundary matrix.

## Deviations

- **Sequential ownership:** P4-03 and P4-04 have the same implementer here,
  so `worker.py` received the §8.6 worker-side memory check in this task's
  commit (it belongs to the memory-guard contract but lives in the
  worker's file). No parallel task was affected.
- **`WorkerInit` moved to `protocol.py`** (created in P4-03's commit inside
  `worker.py`): the pool must import it, and protocol.py is the boundary
  contract module. Clean cutover; `worker.py` imports it from there.
- **Crash attribution is futures-based, not PID-based.** §8.5 attributes
  crashed experiments via the started-event PID map, but a worker killed by
  `os._exit` can lose its `ExperimentStarted` event (the queue's feeder
  thread dies with the child), so PID attribution undercounts. The pool
  reports every experiment whose future did not complete, plus the
  experiment whose future revealed the crash. Queued-but-never-started
  experiments lost to a crash are also marked `worker.crashed` —
  conservative: no experiment is silently lost; the batch continues
  (FR-RUN-06).
- **psutil has no type stubs** (`py.typed` absent) and `types-psutil` is
  not an approved dependency, so the two `import psutil` lines carry
  `# type: ignore[import-untyped]` with a reason. If `types-psutil` is
  approved later, remove both ignores.
- Two deadlock findings fixed during this task (documented for review):
  (1) `_rebuild`/`shutdown` joined the executor's management thread while
  holding the pool lock, which the same thread blocks on in future-done
  callbacks — joins now happen outside the lock; (2) the experiment whose
  future revealed the crash was popped from tracking before attribution,
  losing it from the crash report.
